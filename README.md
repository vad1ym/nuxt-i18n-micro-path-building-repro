# `$localePath({ name })` builds broken paths — duplicated segment + leaked param regex

Minimal reproduction for [`nuxt-i18n-micro`](https://github.com/s00d/nuxt-i18n-micro) **3.24.3**.

▶️ **[Open in StackBlitz](https://stackblitz.com/github/vad1ym/nuxt-i18n-micro-path-building-repro)**
&nbsp;·&nbsp;
[Open in CodeSandbox](https://codesandbox.io/p/github/vad1ym/nuxt-i18n-micro-path-building-repro)

Two symptoms of the same root cause: localized paths are assembled by **string
manipulation** instead of by Vue Router's own path stringifier.

## Measured result

Verified against a clean install of 3.24.3 (`curl` on the SSR output):

| case | generated by `$localePath` | HTTP | correct URL | HTTP |
|---|---|---|---|---|
| **A** dashed route name | `/es/medicos/medicos/x` | **404** | `/es/medicos/x` | 200 |
| **B** param regex constraint | `/es/medicamentos/spain(spain\|poland\|portugal\|italy)` | **404** | `/es/medicamentos/spain` | 200 |

Both strings are emitted straight into `href`, so they end up in crawlable
markup, canonical tags and structured data. Nothing errors.

## Steps to reproduce

1. `npm install && npm run dev`
2. Open `/` — the page prints both generated paths (`data-test="dashed"` and
   `data-test="regex"`).
3. Click either link → 404.

Or non-interactively:

```bash
curl -s http://localhost:3000/ | grep -o 'data-test="[a-z]*">[^<]*'
# data-test="dashed">/es/medicos/medicos/x
# data-test="regex">/es/medicamentos/spain(spain|poland|portugal|italy)
```

## Case A — dashed route name duplicates the parent segment

`doctors-tag` is the name **Nuxt itself generates** for `pages/doctors/[tag].vue`,
so the unsafe form is the default one. Micro treats the `-` as a parent/child
boundary and appends the child's already-absolute localized path to the parent's:

```
doctors      → /medicos
doctors-tag  → /medicos/:tag

$localePath({ name: 'doctors-tag', params: { tag: 'x' } }, 'es')
// → /es/medicos/medicos/x
```

Parent/child nesting is already expressed structurally by Vue Router
(`route.children` / the matched record chain); deriving it from the name string
is both lossy and unnecessary.

## Case B — param regex constraints leak literally

Param constraints (`:page(\d+)`, `:id(\d+)`) are a standard Vue Router feature.
Substitution replaces the `:token` but leaves the `(...)` matcher in place:

```
/medicines/:country(spain|poland|portugal|italy)

$localePath({ name: 'medicines-country', params: { country: 'spain' } }, 'es')
// → /es/medicamentos/spain(spain|poland|portugal|italy)
```

Note the module already knows how to strip these — `extractBaseRoutePattern` in
`@i18n-micro/utils` does exactly that, but only for `:locale(...)`:

```js
e.replace(/\/:locale\([^)]+\)/g, "").replace(/\/:([^()]+)\(\)/g, "/[$1]")…
```

## Suggested fix

Build the path with Vue Router's `stringifyPath` / the compiled route matcher
rather than by concatenating and substituting strings. That fixes both cases at
once: the matcher knows the real parent chain (A) and knows a `(...)` group is a
matcher, not a literal (B).

As a cheaper stopgap, a dev warning when a generated href still contains `(`/`)`
or repeats a segment would surface both immediately.
